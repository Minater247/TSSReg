# TSS / WebReg extension research notes

## System identification
- Old system: UCSD WebReg (`act.ucsd.edu/webreg2`), captured in `webregMain.html` + `webregMain_files/`.
- New system: Triton Student System (TSS, `tss.ucsd.edu/fiori`), an SAP Fiori Launchpad app.
  - The "My Courses" tile is app `itus.mymodules`.
  - Backing OData v2 service: `ITUS.PR_MY_MODULES_V2_SRV` at `/sap/opu/odata/ITUS/PR_MY_MODULES_V2_SRV/`.
  - Responses are Atom+XML by default (`d:` namespace properties), sap-client=500.

## WebReg reference behavior (for building the "legacy view")
- Calendar: customized FullCalendar (`fullcalendar-wr_in-u.js`), agenda week view.
- Status colors (`webreg_in-u.css` ~L594):
  - `wr-grid-en` (Enrolled): `#40798e` bg, white text
  - `wr-grid-wt` (Waitlisted): `#ccffff` bg, black text
  - `wr-grid-pl` (Planned): white bg, `#A0A0A0` text/border (reads as "faded" -- not actual CSS opacity)
  - `wr-grid-ev` (personal event): `#ffffcc` bg
- Conflict detection (in FullCalendar's `eventAfterAllRender`): pairwise interval-overlap
  check (`a.start < b.end && b.start < a.end`) per day+date among currently rendered
  events; if neither is a personal "EV" event, both get `.conflict-cal-event`
  (`2px solid red` border). The non-"top" overlapping event's detail/title gets
  hidden/disabled, but FullCalendar's own agenda layout still slices overlapping
  blocks side-by-side in the same cell.
- Backend calls (`/webreg2/svc/wradapter/*`) are irrelevant to TSS -- totally different backend.

## TSS OData schema (PR_MY_MODULES_V2_SRV) -- entities relevant to a calendar view
- `ModuleHeaderSet` -- one per booked module/section grouping. Key:
  `(SmObjid, SmOtype, ScObjid, ModregId [guid], EventPackageId, AcademicYear, AcademicSession)`
- `ModuleHeaderSet(...)/Event` -- nav property, one entry per class *section* (e.g. LE, DI),
  NOT one per calendar occurrence. Fields that matter:
  - `EventScheduleDays` -- e.g. "MO/WE/FR" (reliable, structured day list)
  - `DayName` / `DayNumber` -- only reflect ONE anchor occurrence, not the full pattern
  - `StartTime` / `EndTime` -- ISO 8601 duration, e.g. `PT10H00M00S` = 10:00:00
  - `EventDate` -- first occurrence date
  - `ScheduleText` -- human string but only shows the anchor day (e.g. "FR 10:00-10:50 ...")
    even when `EventScheduleDays` is "MO/WE/FR" -- TSS's own display bug, don't rely on it for days.
  - `RoomShort` -- **the real WebReg-style building+room code**, e.g. "CENTR 115", "WLH 2005"
  - `RoomStext` -- generic room description, e.g. "Room 115 - Lecture Hall" (no building)
  - `LocationStext` / `LocationShort` -- always "UC San Diego" in observed data (campus-level, useless)
  - `InstrText` -- instructor display name
  - `DeliveryModeText` -- e.g. "In Person"
  - `DStext` / `EventStext` -- section label, e.g. "CSE-123-LE (001-000)" -- use this to correlate
    an Event entry with its DOM block (multiple sections per module).
  - `FreePlaces` / `TotalPlaces` / `WaitlistCapacity*` -- seat counts.
- Full sample response: `tss_odata_sample_event_response.xml` in this folder.
- Confirmed bug: the UI shows `LocationStext + RoomStext` ("UC San Diego Room 115 - Lecture Hall")
  and never surfaces `RoomShort`, even though it's right there in the same response. Purely a
  display omission, not a data-availability problem.

## TSS detail-page DOM structure (course detail view, e.g. "My Courses" > a course tile)
- Rendered by SAPUI5 responsive Form layout. IDs are autogenerated/unstable
  (e.g. `__form4-__vbox22-__list2-0-0--FC-NoHead--Grid`) -- don't hardcode them.
- Stable pattern: each field is two sibling `DIV`s inside the same Grid container:
  - Label cell: `DIV.sapUiFormElementLbl` containing the label text (e.g. "Location / Room")
  - Value cell: `label.nextElementSibling` (no `Lbl` class), containing the value text
- To find a field: walk text nodes for the known label string, then read
  `label.closest(...).nextElementSibling` (see exact traversal depth in prior session --
  in practice: find text node -> parentElement chain up to the `.sapUiFormElementLbl` DIV
  -> `.nextElementSibling` is the value DIV).
- A course with multiple sections (e.g. CSE-123-LE and CSE-123-DI) repeats this whole
  label/value block once per section; correlate each block to its Event entry via the
  section heading text (matches `DStext`/`EventStext`, e.g. "CSE-123-LE (001-000)").
- "My Courses" list-view tiles are NOT plain `<a href>` links (UI5 JS-driven nav), so the
  OData entity key can't be scraped from a tile's href -- confirmed by empty query result.
  Enriching the list view (not just the detail view) will require the extension to issue
  its own supplementary OData calls; enriching the detail view needs zero extra calls since
  all this data is already fetched by the app itself.

## Performance profile (opening one course detail view)
Via `performance.getEntriesByType('resource')`, waterfall for CSE-123 detail open:
```
ModuleHeaderSet          @2422ms  +1066ms   (base entity fetch)
-- then 8 requests fire in parallel --
  Exam            +174ms
  Event           +974ms   <- slowest of the batch
  Person          +100ms
  ModuleGroup     +194ms
  WebLink         +100ms
  ModuleHeaderSet +526ms   <- SAME entity fetched AGAIN, redundant
  IndividualWork  +100ms
  Information     +101ms
-- then serially --
EventPackageSet          @4516ms  +168ms
Template                 @4516ms  +131ms
-- then generic Fiori shell chrome (unrelated to this app) --
notifications, ESH_SEARCH_SRV, personalization containers, badge counts,
two unrelated custom services (ysb_calgrant, ysb_fiori_utils)... 15+ more requests
```
Issues found:
1. `ModuleHeaderSet` fetched twice for the identical key, back to back -- pure waste.
2. No `$batch`/`$expand` -- 7 nav properties each get a full separate HTTP round trip
   instead of one combined call. They run in parallel but each pays full backend
   session/auth overhead separately.
3. Generic Fiori launchpad shell tax (notifications/search/personalization) fires on
   every navigation regardless of the actual app -- baked into the shell, not fixable
   by this app's own code.
None of this is server-fixable from a browser extension, but a content script CAN:
cache `$metadata` (never changes) in localStorage, dedupe identical in-flight requests
via a fetch/XHR interception layer, and prefetch a course's detail data on hover.

## User's explicit architecture preference
Hook fetch/XMLHttpRequest EARLY (document_start, MAIN world, before SAPUI5 boots) to
passively capture the app's own OData responses as they flow through, rather than
having the extension fire its own duplicate/supplementary requests where avoidable.
Only fall back to the extension making its own calls where the app genuinely never
fetches the needed data (e.g. list-view enrichment).
